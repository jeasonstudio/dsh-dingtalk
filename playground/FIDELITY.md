# 演示效果 ↔ 真实钉钉：谁负责哪一块

Playground 的截图看起来"像钉钉"，但里面混着两类东西，用途完全不同：

- **插件真实产出**：`msgContent` 字符串、`flowStatus`、reaction。改了 `src/renderer.ts` / `src/activity.ts` / `src/aicard.ts` 就一定会变，真机上逐字一致。
- **钉钉客户端壳**：头像、气泡、卡片头部、状态点、输入中三点、失败红条、markdown 消息标题、时间分隔条。插件碰不到，它们是钉钉按自己的模板画的；仿真只是为了"看着像"，不代表线上长这样。

界面上的「壳标注」开关会用虚线框圈出第二类。**改观感时先确认自己在改哪一类**：虚线框里的东西改 CSS 是白改。

## 已由真机确认

- **`>` 引用块的换行**：钉钉卡片把相邻的 `> a\n> b` 当成一段（软换行渲染成一个空格）。曾用空行把每步拆成独立引用块，能断行，但每个块都带完整段落间距，六步就把卡片顶掉半屏。
- **多行 = 多段 = 大间距**：真机上 `\n\n` 直接换算成段落间距，过程信息**只能占一个段落**。结论：过程线压成一行普通文字（当前步骤 + 最近 3 步 + 用时），不用引用块、不每步一个 ✅，定稿后最后一段工具行折成一行摘要。由 `renderProcessLine()` 与 `test/renderer-activity.test.mjs` 的「一行、最多一个图标、非引用块」用例锁住。

## 真实钉钉里还要确认的 3 件事

这几条我没法离线证明，建议第一次联调时一次性过完，然后把结论回填到上表：

1. **表格 `align`**：`align="right|center"` 是否生效，还是只认 `style="text-align:…"`。
2. **表格紧贴段落**：确认现在的补空行是不是唯一必要条件（还有没有"表格前后都要空行"之类的坑）。
3. **代码块语言**：` ```ts ` 是否会带语言标签或高亮；不带的话是否影响观感。

## 验收流程（真机）

1. `pnpm run build && dsh web`，用已绑定的机器人在**测试群**里跑四条：
   - 要求画表格 + 代码块（对应 `rich-final`）
   - 要求连续执行两条命令（对应 `process-block` 的过程线 + 收起后的摘要行）
   - 一个长回答，中途在小号里发一句话插话（对应 `interleave` 换卡指针）
   - 一个会失败的回答（对应 `fail`）
2. 同一回合在 playground 里跑对应剧本，逐帧对照：正文是否逐字一致、表格是否同样对齐、过程线与摘要行是否与线上一致、失败文案是否一致。
3. 只把**不一致的地方**记下来 —— 不一致要么归到「钉钉渲染差异」（改我们的写法，如表格补空行），要么归到「客户端壳」（放弃，不要改 CSS 硬凹）。

## 为什么只有这些能控

插件到钉钉之间只有三个可控旋钮：

- `msgContent`（卡片 markdown 文本）—— `src/renderer.ts` 拼、`normalizeCardContent` 规范化
- `flowStatus`（输入中 / 已完成 / 失败）—— `AICard.stream/finish/fail`
- reaction（`🤔思考中`）—— `src/emotion` 相关

除此之外的一切视觉都由钉钉的 AI 卡片模板决定。所以"美化"的空间 = **文案 + markdown 结构 + 状态时序**，这也是 playground 把重点放在帧内容和时间轴上的原因。

> 第 0 轮接入 playground 时，正是靠逐帧核对发现了 `src/renderer.ts` 的真实缺陷（插话后立刻收尾会把同一段正文写进两张卡）。修复见 `test/renderer-interleave-settle.test.mjs`；帧内容与线上字节的等价性由 `test/aicard-payload.test.mjs` 锁死 —— 演示页显示的 `content` 就是 `cardFrameContent()` 的输出。
